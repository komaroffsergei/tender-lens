Спецификации имеют больший приоритет, чем предположения агента. Не добавляй функции «на всякий случай».

## 2. Архитектурные ограничения

Реализуй один монорепозиторий, один Python-пакет, один Dockerfile и три независимо запускаемые роли:

- `crawler`;
- `indexer`;
- `api`.

Инфраструктура:

- один PostgreSQL с расширением `pgvector`;
- один NATS JetStream;
- один Ollama;
- общий Docker volume для вложений.

Запрещено без отдельного ADR и доказанной необходимости:

- Redis, RabbitMQ, Kafka, Celery, Taskiq;
- MinIO/S3;
- Playwright/Selenium;
- LangChain/LlamaIndex;
- Elasticsearch/Qdrant/Chroma;
- Angular/React/Vue/RxJS;
- Kubernetes;
- отдельные базы данных для ролей;
- NATS request/reply для пользовательского поиска;
- outbox/inbox, если спецификация этапа прямо их не потребовала.

NATS используется только для события `tender.changed.v1` между `crawler` и `indexer`.

## 3. Стиль разработки

- Python 3.12 или совместимая стабильная версия, зафиксированная в проекте.
- Идентификаторы, имена файлов, классов, функций и переменных — на английском.
- Документация, docstring и содержательные комментарии — на русском.
- Комментарии объясняют причину, ограничение или неочевидный компромисс. Не комментируй очевидный синтаксис.
- Функции короткие, с одной зоной ответственности.
- Не создавай абстракцию до появления минимум двух реальных реализаций, кроме `SourceAdapter` и минимального AI-клиента для fake/live режимов.
- Не создавай классы-обёртки, которые только передают аргументы следующей функции.
- Не оставляй `TODO`, `pass`, заглушки или неиспользуемый код в завершённом этапе.
- Не меняй сторонние или несвязанные части проекта ради «красоты».
- Любая новая production-зависимость должна быть обоснована в `docs/decisions.md` и добавлена только если стандартная библиотека или текущий стек не решают задачу разумно.

## 4. Spec-driven development

Каждое изменение должно иметь прослеживаемость:

`требование → код → тест → документация`.

При изменении поведения одновременно обновляй:

- соответствующий файл в `specs/`, только если обнаружена ошибка или необходимое уточнение;
- `docs/code-map.md`;
- `docs/progress.md`;
- `docs/traceability.md`;
- README или операционную документацию, если изменились команды, API, переменные среды либо ограничения.

Если реализация требует отклонения от спецификации:

1. останови реализацию конкретного отклонения;
2. создай короткую запись в `docs/decisions.md`;
3. укажи проблему, варианты, выбранный минимальный вариант и последствия;
4. обнови соответствующую спецификацию;
5. только затем продолжай.

## 5. Тестирование

- Сначала реализуй минимальный код этапа, затем обязательные тесты этапа.
- Тесты внешних источников используют сохранённые fixtures и mock HTTP server. Live API не вызывается в обычном CI.
- Тесты Ollama используют детерминированный fake AI provider или HTTP mock. Загрузка моделей в CI запрещена.
- Интеграционные тесты используют настоящий PostgreSQL/pgvector и NATS.
- Перед test commit выполни независимое ревью текущего diff по `.github/codex/prompts/review.md`.
- Любой исправленный дефект получает регрессионный тест с отдельным `REG-XXX` ID.
- Нельзя удалять или ослаблять тест, чтобы получить зелёный CI, если требование не менялось.
- Переход к следующему этапу запрещён при падающих локальных проверках или GitHub Actions.

Обязательные проверки перед каждым тестовым коммитом:

```bash
black --check .
flake8 src tests
mypy src
pytest -q
```

На этапах с контейнерами и интеграцией дополнительно выполняй соответствующие команды из `Makefile`.

## 6. Git и GitHub

- Не переписывай историю опубликованной ветки.
- Не используй `git push --force`.
- Не коммить секреты, локальные модели, вложения из live-сайтов и большие бинарные файлы.
- На каждый этап минимум два коммита:
  1. реализация этапа;
  2. тесты, исправления и синхронизация документации.
- После каждого коммита выполняй push.
- После каждого push дождись результата GitHub Actions.
- При ошибке CI прочитай логи, исправь минимально, добавь регрессионный тест, обнови документацию при изменении поведения, сделай отдельный `fix(stage-XX)` коммит и снова проверь CI.
- Финальное слияние выполняй merge-коммитом, не squash, если права репозитория позволяют.

## 7. Безопасность и честность

- Не выводи и не логируй API-ключи.
- Храни только SHA-256 хеш пользовательского API-ключа.
- Не выполняй обход CAPTCHA, авторизации или технических блокировок.
- Соблюдай задержки и `Retry-After` внешних источников.
- Не утверждай, что команда, push, CI, live-тест или merge выполнены, если нет проверяемого результата.
- При непреодолимом блокере создай `BLOCKERS.md` с точной командой, ошибкой и минимальным действием оператора.

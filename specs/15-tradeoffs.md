# 15. Архитектурные компромиссы

## 1. Три роли вместо строгих микросервисов

**Выбрано:** crawler, indexer и api из одного package/image.

**Почему:** разные процессы и жизненные циклы действительно нужны, но отдельные repositories, dependency graphs и deployment units увеличили бы объём без пользы для тестового.

**Цена:** нельзя независимо версионировать код ролей. Для MVP приемлемо.

## 2. Общий PostgreSQL

**Выбрано:** один database/schema.

**Почему:** отдельные базы потребовали бы catalog API, NATS RPC, дублирование данных и eventual consistency.

**Цена:** роли связаны схемой. Границы записи документированы и проверяются code review, а не физически.

## 3. NATS только для индексации

**Выбрано:** один JetStream subject.

**Почему:** индексация медленная и должна переживать перезапуск. Пользовательский search синхронный и не выигрывает от broker hop.

**Цена:** NATS skill демонстрируется узко, зато по назначению.

## 4. Нет Redis

**Выбрано:** fixed-window limiter в PostgreSQL.

**Почему:** Redis ради одного счётчика создаёт контейнер, конфигурацию и второй state store.

**Цена:** row lock хуже масштабируется, а fixed window допускает boundary burst. При нескольких API replicas/высокой нагрузке переход на Redis sliding window оправдан.

## 5. Общий Docker volume вместо S3/MinIO

**Выбрано:** local volume.

**Почему:** Compose работает на одном host; object storage не нужен для демонстрации.

**Цена:** горизонтальное масштабирование crawler/indexer по разным хостам невозможно без замены storage adapter.

## 6. Exact vector search

**Выбрано:** exact cosine search без HNSW/IVFFlat.

**Почему:** корпус тестового мал, exact даёт предсказуемую полноту и нулевую настройку индекса.

**Цена:** latency растёт линейно. Approximate index добавляется после измерения, а не из архитектурной тревожности.

## 7. Только semantic search

**Выбрано:** embeddings + cosine.

**Почему:** это минимально закрывает RAG-задание.

**Цена:** точные номера, CPV-коды и редкие артикулы могут искаться хуже. Следующее улучшение — PostgreSQL FTS + RRF, но только после benchmark.

## 8. Маленькие локальные модели

**Выбрано:** `qwen3-embedding:0.6b` и `qwen3:1.7b`.

**Почему:** локальный запуск, приемлемая масса, знакомый стек.

**Цена:** качество summarization ограничено. Provider boundary должна позволять заменить модель без изменения API/DB contract, кроме новой reindex.

## 9. Нет outbox/inbox

**Выбрано:** `pending` + republish, `indexed_hash` + JetStream redelivery.

**Почему:** одна таблица состояния уже позволяет восстановить потерянную публикацию и повторную доставку.

**Цена:** нет строгой универсальной exactly-once семантики. Для тестового достаточно и объяснимо.

## 10. Статический JS вместо Angular/React

**Выбрано:** HTML/CSS/JS.

**Почему:** UI состоит из одной формы и списка результатов. Framework не снижает сложность.

**Цена:** при росте экранов и state management понадобится миграция. Сейчас это было бы 700 npm-пакетов для вызова `fetch`, то есть обычная человеческая победа над здравым смыслом.

## 11. Fixtures вместо live CI

**Выбрано:** deterministic fixtures и mock server.

**Почему:** внешний API меняется и может ограничивать запросы; model pull тяжёлый.

**Цена:** live совместимость подтверждается отдельным manual smoke, а не каждым push.

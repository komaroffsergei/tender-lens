# 00. Продукт: TenderLens

## 1. Назначение

TenderLens — минимальная система мониторинга открытых закупок и смыслового поиска по их содержимому.

Система должна:

1. асинхронно получать новые и изменённые закупки из двух открытых источников;
2. приводить разные внешние форматы к одной внутренней Pydantic-модели;
3. сохранять метаданные в PostgreSQL и скачивать вложения;
4. отделять сбор данных от фоновой индексации через NATS JetStream;
5. создавать embeddings локально через Ollama и хранить их в `pgvector`;
6. выполнять релевантный поиск и формировать краткий ответ строго по найденным фрагментам;
7. защищать пользовательские запросы API-ключом и ограничением запросов;
8. запускаться одной командой Docker Compose.

## 2. Основание тестового задания

Основным считается **задание №7**: асинхронный сбор закупок, базовые задержки, скачивание вложений и сохранение метаданных в PostgreSQL.

Функциональные расширения одной реализации:

- задание №3 — embeddings, `pgvector`, поиск релевантных фрагментов и RAG-ответ;
- задание №8 — API-ключ, лимит пять запросов в минуту и HTTP 429;
- задание №9 — Docker Compose и GitHub Actions.

В README итогового репозитория запрещено заявлять, что выполнены четыре независимых задания. Формулировка: «Выбрано задание №7; остальные возможности являются расширениями готового решения».

## 3. Пользователи

### 3.1 Проверяющий тестового задания

Хочет за 5–10 минут:

- запустить проект;
- увидеть две реализации адаптера;
- проверить асинхронный сбор и запись в PostgreSQL;
- увидеть NATS в реально полезной связи;
- выполнить поиск и RAG-запрос;
- получить 429 на шестом запросе;
- посмотреть тесты, CI и документацию.

### 3.2 Технический пользователь

Хочет найти закупки по смысловому запросу и получить краткую выжимку со ссылками на источники.

## 4. Основной пользовательский сценарий

```text
TED / Contracts Finder
        ↓
асинхронный crawler
        ↓
нормализованный TenderRecordV1
        ↓
PostgreSQL + вложения в volume
        ↓
tender.changed.v1 в NATS JetStream
        ↓
indexer: extract → chunk → embed
        ↓
pgvector
        ↓
FastAPI: /search или /ask
        ↓
статический HTML-интерфейс
```

## 5. Критерии успеха продукта

Продукт считается успешным, если доказан следующий вертикальный путь:

1. fixture или live-источник возвращает закупку;
2. адаптер создаёт валидный `TenderRecordV1`;
3. повторный сбор не создаёт дубль;
4. изменение данных меняет `content_hash`;
5. crawler публикует событие только для новой или изменённой закупки;
6. indexer создаёт чанки и embeddings;
7. `/api/v1/search` возвращает релевантные источники;
8. `/api/v1/ask` возвращает ответ, основанный только на этих источниках;
9. шестой ограничиваемый запрос одного API-ключа получает 429;
10. весь путь проверяется автоматическим e2e-тестом без live API и без загрузки моделей в CI.

## 6. Принцип минимальности

Каждый компонент допускается только при наличии конкретной обязанности в основном сценарии. В MVP отсутствуют Redis, frontend-фреймворк, отдельный catalog-service, отдельные базы, MinIO, LangChain, OCR и approximate vector index. Их отсутствие является сознательным решением, а не пропущенной работой.

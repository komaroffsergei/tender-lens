# 02. Требования и критерии приёмки

Статусы требований: `MUST`, `SHOULD`, `MAY`. В MVP реализуются все `MUST`.

## 1. Сбор данных

### FR-CRAWL-001 — единый контракт адаптера (`MUST`)

Каждый источник реализует `SourceAdapter` и возвращает `TenderRecordV1`.

**Приёмка:** TED и Contracts Finder проходят один параметризованный contract-test; код orchestration не содержит `if source == ...` для нормализации полей.

### FR-CRAWL-002 — два источника (`MUST`)

Реализованы `TedAdapter` и `ContractsFinderAdapter`.

**Приёмка:** fixture каждого источника превращается в валидную одинаковую внутреннюю модель.

### FR-CRAWL-003 — асинхронность и ограничение конкурентности (`MUST`)

Сетевые операции неблокирующие, число одновременных запросов ограничено конфигурацией.

**Приёмка:** тест с instrumented mock transport подтверждает, что одновременно выполняется не более заданного количества запросов.

### FR-CRAWL-004 — вежливое поведение (`MUST`)

Crawler использует настраиваемую задержку, jitter, timeout, retry и `Retry-After`; не обходит CAPTCHA или авторизацию.

**Приёмка:** тесты 429, 503, timeout и исчерпания попыток; README описывает этическое ограничение.

### FR-CRAWL-005 — инкрементальный обход (`MUST`)

Курсор источника обновляется только после успешной обработки полученной порции.

**Приёмка:** ошибка внутри порции не продвигает cursor; повторный запуск безопасно повторяет обработку.

### FR-CRAWL-006 — сохранение закупки (`MUST`)

Новая закупка создаётся, неизменённая не порождает повторную индексацию, изменённая получает новый `content_hash` и `index_status=pending`.

**Приёмка:** три соответствующих интеграционных теста.

### FR-FILE-001 — скачивание вложений (`MUST`)

Вложения скачиваются потоково в общий volume, имя нормализуется, размер ограничивается, SHA-256 сохраняется.

**Приёмка:** успешная загрузка, path traversal, превышение размера, обрыв, повторная загрузка и дедупликация покрыты тестами.

### FR-FILE-002 — типы для индексации (`MUST`)

Индексируются PDF с текстовым слоем, XML, HTML, JSON и TXT. Остальные файлы сохраняются, но помечаются как неподдерживаемые для извлечения текста.

**Приёмка:** unsupported-файл не ломает обработку тендера.

## 2. Контракты и данные

### FR-DATA-001 — минимальная схема (`MUST`)

База содержит ровно пять предметных таблиц, перечисленных в `04-data-model.md`.

### FR-DATA-002 — уникальность (`MUST`)

Пара `(source_id, external_id)` уникальна.

### FR-DATA-003 — исходные данные (`MUST`)

Исходный payload сохраняется в `raw_payload JSONB`, но пользовательский API не возвращает его по умолчанию.

### FR-HASH-001 — детерминированный hash (`MUST`)

`content_hash` вычисляется из канонического набора нормализованных полей и стабильного порядка вложений, без timestamps обработки.

**Приёмка:** перестановка ключей JSON не меняет hash; изменение значимого поля меняет hash.

## 3. NATS и индексация

### FR-NATS-001 — единственное событие (`MUST`)

Crawler публикует `tender.changed.v1` после commit новой или изменённой закупки.

### FR-NATS-002 — долговечность (`MUST`)

Используется JetStream, stream и consumer создаются идемпотентно, ACK выполняется только после успешной индексации.

### FR-NATS-003 — минимальный payload (`MUST`)

Событие содержит `schema_version`, `event_id`, `occurred_at`, `tender_id`, `content_hash`.

### FR-NATS-004 — восстановление после publish failure (`MUST`)

Если публикация не удалась, тендер остаётся `pending`; следующий цикл повторно публикует pending-записи.

### FR-INDEX-001 — извлечение текста (`MUST`)

Indexer собирает текст из нормализованных метаданных и поддерживаемых вложений.

### FR-INDEX-002 — чанкинг (`MUST`)

Текст разбивается по абзацам; chunk не длиннее 1500 символов; overlap не больше 150; пустые chunks не сохраняются.

### FR-INDEX-003 — embeddings (`MUST`)

В live-режиме вызывается Ollama `/api/embed` пакетно. Размер каждого вектора равен 1024.

### FR-INDEX-004 — идемпотентность (`MUST`)

Если `indexed_hash == event.content_hash`, событие подтверждается без повторной записи chunks.

### FR-INDEX-005 — атомарная замена индекса (`MUST`)

Удаление старых и запись новых chunks выполняются одной транзакцией. При ошибке старый индекс остаётся доступным.

## 4. Поиск и RAG

### FR-SEARCH-001 — semantic search (`MUST`)

Запрос преобразуется той же embedding-моделью, затем выполняется точный cosine search по chunks.

### FR-SEARCH-002 — выдача (`MUST`)

Каждый результат содержит `tender_id`, `title`, `source`, `source_url`, `snippet`, `score` и при наличии attachment metadata.

### FR-SEARCH-003 — лимит результатов (`MUST`)

`limit` от 1 до 10, по умолчанию 5.

### FR-RAG-001 — grounded answer (`MUST`)

`/ask` использует только top 5 найденных chunks. Prompt запрещает добавлять факты вне контекста.

### FR-RAG-002 — отсутствие данных (`MUST`)

Если retrieval ничего не нашёл выше минимального технического порога или индекс пуст, LLM не вызывается; ответ: `Недостаточно данных для ответа.`

### FR-RAG-003 — источники (`MUST`)

Ответ содержит список реально использованных результатов retrieval. Не допускаются несуществующие ссылки.

### FR-RAG-004 — ошибка модели (`MUST`)

Timeout/5xx/некорректный ответ Ollama преобразуется в 503 и не подменяется выдуманным ответом.

## 5. API, ключи и ограничение запросов

### FR-AUTH-001 — API key (`MUST`)

Защищённые endpoints требуют `X-API-Key`; хранится только SHA-256 hash.

### FR-AUTH-002 — создание ключа (`MUST`)

CLI создаёт криптографически случайный ключ и печатает открытое значение ровно один раз.

### FR-RATE-001 — лимит (`MUST`)

`/search` и `/ask` используют общий fixed UTC-minute counter конкретного API-ключа. Default: 5 запросов/минуту; значение настраивается в записи ключа.

### FR-RATE-002 — атомарность (`MUST`)

Проверка и увеличение счётчика выполняются в транзакции с row lock.

### FR-RATE-003 — ответ 429 (`MUST`)

Шестой запрос в одном окне получает 429 и `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.

### FR-API-001 — документированный контракт (`MUST`)

OpenAPI соответствует `06-api.md`; ошибки имеют единый JSON-формат.

### FR-API-002 — health (`MUST`)

`/health/live` подтверждает жизнь процесса; `/health/ready` проверяет БД, NATS для фоновых ролей и Ollama в зависимости от роли/режима.

## 6. UI

### FR-UI-001 — статический клиент (`MUST`)

UI реализован на HTML/CSS/JavaScript и раздаётся FastAPI. Нет npm, CDN и frontend-framework.

### FR-UI-002 — безопасность ключа (`MUST`)

Ключ не hardcoded, не передаётся в URL и хранится только в `sessionStorage`.

### FR-UI-003 — состояния (`MUST`)

Интерфейс показывает loading, empty, success, validation error, 401, 429, 503.

### FR-UI-004 — безопасный вывод (`MUST`)

Данные вставляются через `textContent` или эквивалентный безопасный DOM API; `innerHTML` с внешними строками запрещён.

## 7. Нефункциональные требования

### NFR-MAINT-001 — понятность (`MUST`)

Один Python package, один Dockerfile, три роли. Не добавляются архитектурные слои без функции.

### NFR-DOC-001 — русская документация (`MUST`)

README, specs, docstrings и содержательные комментарии на русском. Идентификаторы на английском.

### NFR-DOC-002 — синхронизация (`MUST`)

Любое изменение поведения обновляет `docs/code-map.md`, `docs/traceability.md` и релевантную документацию в том же этапе.

### NFR-TEST-001 — изоляция CI (`MUST`)

Обычный CI не обращается к live-источникам и не загружает модели Ollama.

### NFR-CI-001 — обязательные проверки (`MUST`)

На push и pull request выполняются black, flake8, mypy, unit, integration/e2e, migration check, Docker build и Compose validation.

### NFR-SEC-001 — секреты (`MUST`)

Секреты отсутствуют в Git, логах, fixtures и образах.

### NFR-OPS-001 — воспроизводимость (`MUST`)

Проект запускается по README на чистой машине с Docker Compose; все переменные описаны в `.env.example`.
